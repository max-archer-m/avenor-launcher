# 产品决策与范围变更治理

> 英文语义源：[product-decisions.md](product-decisions.md)。
>
> 本文定义产品决策与范围变更的处理方式，不定义首个里程碑的内容，也不授权进入实现。

## 目的

在产品设计和开发暴露新信息时，允许产品继续演进，同时保持产品意图、实现证据和项目进展一致。

产品文档记录当前产品契约。当用户证据、技术证据或项目作者的判断支持其他方向时，该契约可以变更。已存在的代码不会静默覆盖产品契约，已存在的文档也不应阻止作者决定的变更。

## 决策权与责任

- 项目作者是所有项目事项的最终决策人和第一责任人。
- 产品、项目和技术角色在各自职责内提供分析、备选方案、证据和建议，但不取代作者的最终决策权。
- 安全、隐私、法务、财税或平台政策结论需要相关专业能力时，仍必须获得专业复核。
- 技术证据可以触发产品决策的重新评估，但某个实现选择不会因为已写入代码就自动成为产品决策。

## 权威信息来源

各类信息使用各自的权威来源：

| 问题 | 权威来源 |
| --- | --- |
| 产品为什么存在、适用哪些长期边界 | 产品概览 |
| 用户应当能观察和完成什么 | 当前需求和交互规格 |
| 重要产品方向或范围为何变更 | 本文中的产品决策记录 |
| 项目在交付生命周期中处于什么位置 | 里程碑或项目进展记录 |
| 系统如何设计和实现 | 架构文档和技术决策记录 |
| 当前实现实际做了什么 | 代码、测试、构建和验证证据 |
| 当前产品契约是否已满足 | 可追踪的验收与验证证据 |

当文档、实现与已观察的平台行为不一致时，应记录契约不一致并显式解决，不得假定最旧文档或当前代码自动胜出。

## 产品范围层级

使用以下计划层级：

1. **能力层级：** 长期产品能力边界，例如 V1 固定呈现或 V2 基础适应。能力层级不自动等同于语义化软件版本。
2. **里程碑：** 围绕一个主要产品结果及明确出口证据组织的项目单元。
3. **垂直切片或 Feature：** 可以独立理解、演示和验证，且已写入当前产品契约的用户结果。
4. **实现任务：** 交付当前切片或 Feature 所需的工程工作，其本身不是产品结果。
5. **Patch 或 Bug fix：** 在不扩大产品契约的前提下，恢复当前已记录行为的工作。

不得按照固定功能数量定义里程碑或 tag。功能数量可作为计划预警，但应以内聚性、用户结果、依赖、风险和证据确定边界。

一个里程碑通常只应有一个主要产品结果。如果其包含超过三条相互独立的主要用户旅程，应复核是否需要拆分。这是复核触发条件，不是自动规则。

## Tag 与发布

Git tag 标识一个实现快照。它是交付证据，不是产品范围层级，也不代替里程碑记录。

- 一个里程碑可以没有 tag、有一个 tag，或有多个候选与验证 tag。
- tag 可以代表垂直切片构建、里程碑候选版本、验证基线、Patch 或公开发布。
- 只有在实际构建和发布流程存在后，才定义 tag 命名、版本、签名与发布门禁。
- 本文不授权创建 tag 或发布。

## 里程碑记录

里程碑记录描述项目意图、进展、证据和结果，不替代产品需求。

里程碑记录可以包含：

- 当前追求的主要产品结果
- 状态和责任人
- 当前产品基线及所含切片或 Feature 的链接
- 准入和准出条件
- 进展与已完成证据
- 阻塞项和未解决的契约不一致
- 相关产品决策和技术决策记录的链接
- 已记录的原范围快照偏差
- 最终的完成、部分完成、取消、暂停或被替代结论
- 存在时的相关构建、tag 或验证记录

里程碑记录不得成为详细页面行为、验收标准、架构或实现规则的第二份权威副本。当关联的产品契约变更时，里程碑记录应记录该变更及决策链接，而不是静默改写历史。

首个里程碑仍待单独讨论和定义。

## 什么是产品范围变更？

产品范围变更是对当前产品契约的新增、删除、推迟、替换或实质性修改。

变更影响以下任一内容时，按范围变更处理：

- 目标用户或支持的场景
- 能力层级边界或长期非目标
- 里程碑的主要产品结果或出口门禁
- 已纳入或排除的页面、弹窗、用户旅程或可独立使用的功能模块
- 支持的操作系统、设备、屏幕形态、语言、地区或发行渠道
- 用户可见行为、状态、恢复或验收标准
- 数据类别、权限、package visibility、联网、账号、云服务、分析或第三方处理
- 无障碍、隐私、安全、兼容性或维护义务

详细交互规格可以页面、弹窗或相对独立的功能模块作为文档拆分单位。文档组织方式本身不决定是否发生范围变更。

以下情况通常不属于范围变更：

- 在不改变规范含义的前提下修正文字
- 澄清当前契约中已存在的行为
- 修复不满足现有验收标准的实现
- 不产生用户可见或契约影响的内部重构
- 不改变当前行为或质量要求的小幅展示调整

## 决策影响等级

按影响将产品决策分类：

### D1：战略决策

D1 决策改变能力层级边界、核心原则、目标受众、主要平台或设备边界、数据立场、发行模式或其他长期产品约束。

要求：

- 记录产品决策。
- 更新产品概览及所有受影响的权威需求。
- 重新评估受影响的里程碑和专业复核需求。

### D2：范围决策

D2 决策在不重新定义产品长期方向的前提下，改变当前里程碑、垂直切片、Feature、用户旅程、非目标或验收标准。

要求：

- 记录产品决策。
- 更新受影响的 Requirements Brief 或交互规格。
- 存在里程碑时，记录其所受影响。

### D3：局部产品决策

D3 决策在不改变当前范围的前提下，选择或澄清局部页面或交互行为。

要求：

- 将结果记入适用的交互规格。
- 仅在备选方案、影响后果或未来可能重新评估使得理由具有长期价值时，单独记录产品决策。

## 必须记录决策的触发条件

出现以下任一情况时，建立产品决策记录：

- 变更属于 D1 或 D2。
- 存在多个合理方案，且其影响存在实质差异。
- 决策难以或需要较高成本才能回退。
- 同一问题未来很可能再次被提出。
- 决策影响多份权威文档或多个 Feature。
- 变更新增数据、权限、联网、账号、外部服务、支持平台或发行义务。
- 因技术证据推迟、删除或替换当前需求。
- 里程碑发生实质性范围调整、暂停、取消或被替代。

普通文字修改、常规缺陷修复或不影响产品契约的实现细节不建立决策记录。

## 契约不一致处理

修改产品文档或实现前，先对不一致进行分类：

### 文档澄清

当前契约没有改变，但文档不完整或存在歧义。应澄清权威产品文档。除非理由会产生重要影响，否则可不单独记录决策。

### 实现缺陷

当前契约清晰，但实现不满足该契约。应修复代码和验证证据，不得仅为了匹配缺陷而修改产品文档。

### 产品范围变更

新认知导致作者改变当前用户行为、范围或验收标准。应更新受影响的产品文档，然后对齐实现与测试；仅在作者主动启用决策记录后记录该决策。

### 需要重新考虑产品的技术约束

平台或实现证据表明当前契约不可行、不可靠、不安全或成本与当前条件不成比例。应记录证据和备选方案，获得作者的产品方向，然后更新适用的产品和技术文档。

### 探索性实现

无法通过其他方式获得证据时，原型或技术 Spike 可以先于当前产品文档。在所得行为按作者方向写入适用权威文档前，其不属于当前产品契约。

## 变更流程

使用与影响相匹配的最轻流程：

1. 识别已观察问题、证据、受影响契约与目标结果。
2. 将其分类为澄清、缺陷、范围变更、技术约束或探索。
3. 涉及产品决策时，确定 D1、D2 或 D3 影响等级。
4. 向项目作者提供有意义的备选方案和影响。
5. 将作者方向反映到当前权威文档中；只有作者主动启用决策记录后才新增决策记录。
6. 更新所有受影响的权威产品文档。
7. 仅在变更后的当前契约范围内更新实现和测试。
8. 在不复制产品契约的前提下，更新里程碑进展和验证证据。

局部澄清或小型产品调整可在同一个聚焦提交中同步更新文档、代码和测试。对于 D1 或 D2 变更，变更后的当前产品契约必须在实现之前或与实现一同可供评审。已经存在的代码不会静默改变产品契约。

## 产品决策记录格式

使用稳定且永不复用的标识符，将记录追加到本文：

```markdown
## PD-0001: <Decision title>

- Date: YYYY-MM-DD
- Impact: D1 | D2 | D3
- Decider: Project author
- Context: <为什么需要作出决定>
- Decision: <项目作者确立的方向>
- Alternatives: <曾考虑的有意义备选方案>
- Rationale: <为什么选择该方向>
- Scope impact: <受影响的能力层级、里程碑、切片、Feature 或非目标>
- Documentation impact: <要更新的权威文档>
- Technical or professional review: <必要时的证据或专业复核>
- Revisit when: <触发重新评估的条件>
- Related records: <需求、里程碑记录、ADR、验证或替代决策>
```

- 每条记录只聚焦一个可独立重新评估的决策。
- 决策记录不复制完整需求或技术设计，而是链接到它们的权威位置。
- 不得改写历史决策以表示后来的结果。应新增记录解释变化，并互相链接。
- 一个里程碑可链接多个产品决策，一个产品决策也可影响多个里程碑或 Feature。

## 当前编写暂停规则

- 在项目作者主动要求开始记录产品决策前，不得追加任何实际 `PD-NNNN` 记录。
- 上述模板是格式定义，不是已存在的决策记录。
- 暂停期间，作者的明确决定可以直接更新适用的权威产品文档。不得仅因通常属于必须记录的触发条件就新建产品决策记录。
- 作者允许开始记录后，从 `PD-0001` 开始；除非作者明确要求重建历史，否则不得追溯编造记录。

## 当前边界

本治理规则只建立决策流程，不：

- 定义首个里程碑
- 授权垂直切片或实现任务
- 选择技术栈或架构
- 定义 tag 或发布策略
- 授权 V2、V3 或 V4 工作
- 授权公开分发或商业化
- 在项目作者明确要求前授权写入实际产品决策记录
