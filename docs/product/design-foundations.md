# Product Design Foundations

> Public semantic source: English. Chinese counterpart: [design-foundations.zh-CN.md](design-foundations.zh-CN.md).

## Current theme

- All Avenor surfaces use the dark theme regardless of whether the surface itself paints an opaque background. Text, icons, controls, and semantic color roles use their dark-theme presentation.
- Home and Drawer paint no visible application background. Their surface, status-bar region, and navigation-bar region request full transparency so the system background beneath Avenor remains visible.
- Avenor does not add a persistent backdrop gradient, fixed scrim, blur, glass effect, or other contrast-protection layer to Home or Drawer in the current product contract. This does not prohibit a transient, local interaction cue such as the application-drag edge indicator defined below. A future Drawer glass or blur treatment is an additive capability and is not defined now.
- Settings uses an opaque standard Material 3 dark color scheme. Use Material semantic roles such as `surface`, `onSurface`, and related container roles instead of inventing page-specific dark hex colors. Final resource values remain part of the design-token work.
- Modal sheets remain dark. Their presentation must preserve light status-bar icons.
- Avenor requests transparent system bars on Home and Drawer and leaves platform or device contrast enforcement at its default behavior. It does not disable, replace, or duplicate system contrast protection.
- The system navigation mode and navigation controls remain visible according to the user's system configuration; Avenor does not enter immersive mode or hide system navigation.
- Theme customization is an additive future capability and is outside the current contract.

## Layout

- Product spacing values are semantic design tokens rather than arbitrary per-screen literals.
- Layout and reachability decisions primarily optimize for right-hand holding with right-thumb input and left-hand holding with right-hand tapping. Other postures are secondary considerations rather than equal optimization targets.
- Home uses `16dp` horizontal and vertical content padding. Adjacent visible Home modules use `16dp` spacing.
- Application-action-sheet dividers use `16dp` horizontal inset.
- Home is a fixed, non-pageable surface. Its favorite-list area currently contains at most two equal-status vertical lists without folders or another reveal surface; each list scrolls independently only when its content exceeds the shared viewport.
- Home uses content-driven vertical sizing and does not scroll vertically as a whole. The basic-information module wraps its required content and interaction targets. When the natural favorite-list and populated-secondary heights plus their `16dp` separation fit the remaining safe height, both remain at natural height and favorite lists do not scroll. On overflow, the secondary area retains its natural ribbon height and the favorite-list area receives the remaining viewport above it; only an overflowing list scrolls vertically. The full-width secondary area has zero height without content and contains at most five `56dp`-high horizontal ribbons, each independently scrolling horizontally only when its fixed-width entries overflow.
- Home's favorite-list composition uses `8dp` internal padding on each side and a `16dp` inter-list gap. One list takes the complete available composition width; two visible lists divide the remaining width equally. Width is derived from visible-list count rather than a fixed percentage. Lists share one viewport height and keep independent content and scroll state. Empty persisted lists do not exist.
- Favorite size is a list-level token. Large uses a `48dp` icon, `64dp` item height, and `18sp/28sp` normal-weight name; medium uses `40dp`, `56dp`, and `16sp/24sp`; small uses `32dp`, `48dp`, and `14sp/20sp`. Every newly created or migrated list starts at medium; the edit-mode list-size control selects and persists large, medium, or small independently for each persisted list. All sizes use a `16dp` icon-to-name gap, system font scaling, static one-line end-ellipsized names, and `8dp` item padding where geometry permits. Normal and edit modes preserve the stored list size. Every list uses a `24dp` drag-handle graphic inside a `48dp`-wide hit region; its height follows the current item height.
- In Home edit mode, each currently defined editable module receives the same subtle translucent light-gray editing surface with a small corner radius. The basic-information, favorite-list, and populated secondary-favorites modules receive this module-level surface. Each secondary ribbon additionally uses its own `1dp` light-foreground boundary at `12%` opacity and `12dp` corner radius while keeping its interior transparent. The module surface sits behind content rather than tinting it and does not imply that the basic-information module is editable. Exact shared surface color, opacity, and radius tokens remain subject to visual calibration.

- Secondary-favorite entries use fixed, non-selectable medium dimensions: a `40dp` icon, `56dp` item height, `16dp` icon-to-name gap, and one static end-ellipsized `16sp/24sp` normal-weight name line. The vertical-list size menu does not apply to ribbons. The icon is the primary recognition cue and the name is a secondary visual label. Items have a fixed width of `128dp`, remain left-aligned with `8dp` between items, and do not redistribute unused ribbon width. Adjacent ribbons use `8dp` vertical spacing. Each item uses the light foreground semantic color at `6%` opacity as its background, the same semantic color at `12%` opacity for a `1dp` boundary, and a `12dp` corner radius; the current light ripple remains its press feedback. Current ribbons reserve no title height.
- Application-level drag auto-scroll uses a non-interactive edge cue rather than a full-container overlay. The cue is a `48dp` inward gradient derived from the light foreground semantic color, rising from transparent on the content side to no more than `8%` opacity at the active edge. It appears only while that direction can continue scrolling, never intercepts input or changes geometry, and remains below insertion and exchange feedback.
- Home edit-mode add controls use a `24dp` plus graphic inside an interaction target at least `48dp` wide and high. Drawer uses a fixed `56dp`-high transparent top app bar below the status-bar safe inset; its ordinary Back arrow uses the same `24dp` functional-icon token and a `48dp` interaction target.
- Home edit-mode remove controls use a visible `24dp` circular error-semantic badge containing a `14–16dp` X. The badge overlaps the logical top-start edge of the application icon without hiding its primary identifying artwork or a platform clone/profile badge. Its invisible interaction target is at least `48dp × 48dp`, may overlap the non-launchable icon region in edit mode, and does not reserve a separate horizontal action column. The trailing `24dp` drag-handle graphic likewise retains its `48dp`-wide full-item-height target without requiring a visibly wide control.
- A persisted vertical favorite list uses a fixed `48dp`-high edit-mode control bar with three equal slots at physical left, center, and right. Remove-list, size, and reorder-list controls use a `40dp` circular visible container centered in separate `48dp × 48dp` targets. Remove and reorder use `24dp` functional icons; size uses the current localized single character at a fixed type size. Remove uses error semantics, while size and reorder use the light-foreground role. These list-level circular controls are an explicit exception to the global ripple rule: their only press indication is a short increase in container opacity, retained throughout an active reorder drag. Physical left-to-right placement does not mirror for RTL locales.
- The list-size menu uses three `64dp` Material menu rows and one selection target per row. Physical content order is single-selection indicator, bundled Android-default generic application icon preview, then localized label, without RTL mirroring. The same packaged icon resource appears at `48dp`, `40dp`, and `32dp`; it is decorative, has no badge, and is never loaded at runtime. Complete rows use bounded ripple and platform dark-surface elevation.
- An editable secondary ribbon uses fixed `48dp × 56dp` control rails outside its central application viewport: remove-ribbon at logical start and ribbon reorder at logical end. Their visible `24dp` X and drag-handle graphics remain distinct from application-level controls, and subtle `1dp` dividers separate the fixed rails from scrolling content. The rails reduce only the edit-mode viewport; they do not resize `128dp` application items. One persisted ribbon hides reorder presentation and interaction while preserving the end rail; at least two persisted ribbons show it. A provisional ribbon exposes neither rail action.

## Typography

- Typography follows system font scaling.
- Time uses a `57sp/64sp` bold display role with tabular numerals where supported.
- Date, weekday, application names, and ordinary information use the Material 3 `bodyLarge` reference of `16sp/24sp` unless a component specification defines another semantic role.
- Application names remain one line and static. A name that does not fit uses end ellipsis; Avenor does not use marquee motion for application names.
- Font scaling beyond the current personal-use layout is not separately optimized. Text remains clipped to its one-line component boundary if extreme system scaling exceeds that boundary.
- Settings primary titles use `titleMedium` (`16sp/24sp`) with `onSurface`; supporting text uses `bodySmall` (`12sp/16sp`) with `onSurfaceVariant`; centered secondary information items use `titleSmall` (`14sp/20sp`) with `onSurfaceVariant`.

## Icons and application identity

- Functional icon sizes describe the visible icon artwork, not its container or interaction boundary. A standard functional icon is `24dp × 24dp`. This token applies to ordinary icon buttons, action icons, application-shortcut icons, Home edit-mode add controls, the Drawer Back arrow, Settings trailing arrows, and other current controls unless a component specification explicitly defines another size. If an applicable page contract later introduces a visible Back arrow on Settings or Pixel-style leading icons for Settings items, those icons also use this standard token.
- A standard functional icon that is independently interactive remains inside a focusable touch target of at least `48dp × 48dp`. When an icon and label form one action, the complete combined item is one interaction and accessibility target; the icon does not create a second target.
- A non-interactive status icon is `40dp × 40dp`. This token applies to standalone loading-result, empty-state, or error illustration icons when the applicable component defines one. The status icon does not receive its own touch target or ripple; any adjacent action remains a separate control.
- Functional and status icons use the applicable semantic content color and consistent optical weight. A `24dp` or `40dp` viewport must not be filled with disproportionately small artwork merely to satisfy the nominal token.
- An icon-only control has a localized accessibility name. A decorative icon, or an icon whose adjacent label already names the same combined action, does not expose a duplicate accessibility description.
- Defining an icon-size token does not by itself add the corresponding control to a page. The Drawer contract currently includes its Back arrow. A Settings Back arrow and Settings leading-item icons appear only if the applicable page or navigation contract explicitly includes them; their mention here establishes visual sizing only.
- Native adaptive application icons follow the current device mask, such as a device-specific circular or squircle presentation.
- A legacy icon without adaptive layers is normalized inside the current device mask while keeping its complete identifying artwork recognizable within a safe region.
- Clone or profile badges use platform-provided data, are applied after shape normalization so the mask does not crop them, and remain consistent across Home, Drawer, and related application UI.
- Drawer uses a `40dp × 40dp` visible application icon inside an application row at least `56dp` high. Home uses the large, medium, and small list-level dimensions defined above.
- In Drawer, the icon and application name are vertically centered in the row, with `16dp` between the visible icon boundary and the application-name region.
- The complete Drawer row remains the selection and long-press target; its `40dp` icon is a visual size, not a restriction on the row touch target. Home interaction-target geometry follows the large, medium, and small favorite-size tokens defined above and the applicable Home component specification.
- If an application's icon cannot be loaded, use Android's platform-default generic application icon in the applicable Home or Drawer visual region and apply the same shape-normalization and badge rules. Do not leave the region empty or substitute an unrelated Avenor icon.
- Current target devices are expected to provide clone or profile badges. Avenor does not add its own fallback badge or secondary identity label when the platform provides none. Such fallback identity treatment is an additive future capability.
- Exact parity with proprietary OEM shadows, icon packs, theme services, or other Launcher-specific effects is not required by the current product contract.

## Interaction and accessibility

- Interactive controls should provide a focusable touch target of at least `48dp × 48dp`, following Android accessibility guidance, even when their visible content is smaller. This is the default lower bound and must not be reduced without a component-specific, author-accepted reason supported by focused device evidence; dense layouts should first separate visual size from hit geometry or use non-conflicting overlap.
- The Home time row is at least 64dp high. The date row is 48dp high and directly provides its focusable touch target.
- Pressed, focused, selected, and disabled states must not rely on color alone.
- Every enabled target that performs a click or long-press action provides a bounded Material ripple from the initial press unless a component contract defines another visible press state. The ripple is clipped to the target's actual interaction boundary and follows its applicable shape; it must not spill across adjacent items or imply that a larger region is interactive. Vertical-list-level circular edit controls use their explicitly defined opacity-only press state instead.
- Under the current dark-theme contract, the ripple uses a subtle low-opacity near-white color derived from the light foreground-content role. Its exact color and opacity are shared semantic design tokens rather than page-specific values.
- Ripple indicates that input is being pressed; it does not confirm that an action succeeded. A long-press target shows the same press ripple before the long-press threshold and provides its separately defined haptic feedback only when the long press is recognized.
- If input becomes a scroll, drag, surface-transition gesture, cancellation, or other non-click interaction, the press indication is cancelled without triggering the click action. Disabled targets do not present an actionable ripple.
- A future light theme must use a ripple derived from its foreground-content role with visible contrast against the affected surface. It is not required to retain the current near-white ripple. This cross-theme rule does not add light-theme support to the current product contract.
- Haptic feedback respects system availability and user settings. Current semantic feedback types are long-press confirmation and short index or edit-movement steps; exact platform constants require implementation validation.
- Drag semantics are container-based. Crossing another body within one vertical list, one ribbon, or the ribbon-order list exchanges and persists immediately; same-container gaps never insert. Crossing to a different application container shows either an occupied-body exchange highlight or a gap insertion line, and persists one operation only on valid release. A cross-container preview keeps its source size until release, after which the target container's presentation applies.
- Small-screen-specific layout and TalkBack-specific alphabet-index behavior are outside the current personal-use scope. The index instead uses fixed 20dp slots and becomes scrollable when its maximum 28-slot model does not fit within 560dp of available height.

## Resource-backed values

User-facing strings, colors, dimensions, and other reusable presentation values must be resource-backed and localizable or themeable as applicable. They must not be scattered as hard-coded literals in product UI code. The exact Android resource and Compose access structure belongs to the future technical architecture.
