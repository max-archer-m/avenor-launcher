# 迭代记录格式

> 英文语义源：[iteration-record-format.md](iteration-record-format.md)。

## 目的与命名

每个 `docs/delivery/<version>/` 目录从规划到完成始终在 `delivery.md` 同级保存该版本的迭代记录。每个迭代是边界明确、可独立评审并服务于一个正式版本的交付单元。

文件名使用 `iteration-<number>-<title>.md`，全项目采用从 `1` 开始、单调递增的正整数唯一序列，例如 `iteration-1-home-minimum-usable-surface.md`。不得重编号、复用或重启序列，也不添加前导零。`<title>` 使用简短的小写英文 slug。

维护中文对应文档时，在 `.md` 前追加 `.zh-CN`，例如 `iteration-1-home-minimum-usable-surface.zh-CN.md`。中文文档使用相同迭代编号和英文 slug。

## 必需格式

新迭代记录使用以下结构。获得授权后可通过修改本文调整格式；已有历史记录不因后来格式变化而重写。

中文对应文档可以翻译标题和章节标题，但必须与英文语义源保持相同的章节顺序、范围和规范含义。

## 迭代推进与验证政策

Avenor Launcher 当前由项目作者作为个人项目维护。因此，迭代记录中的验证场景默认是降低风险、完善证据的建议，不自动构成本迭代或下一迭代的准入或准出门禁。

- 每份迭代记录必须且只能使用以下封闭枚举中的一个状态值：`Planned`、`In Progress`、`Completed` 或 `Cancelled`。不得引入同义词、限定后缀或其他状态值。
- `Planned` 允许按作者方向随时调整迭代内容，并允许为确认范围可行性开展技术调研；不得开发生产代码。调研产出在作者授权实施且状态变为 `In Progress` 前只能作为证据或提案。
- `In Progress` 从项目作者授权生产代码开发时开始。已授权范围内的文档、代码、测试和本地验证可以继续进行。开发中仅可慎重进行保留迭代目标和当前产品定义的小范围调整，并记录原因和受影响边界。若调整会实质替换目标、主要结果、产品范围、架构方向、依赖顺序或验证义务，通常应取消或替换迭代，而不是静默重写。
- `Completed` 表示已授权实现完成、项目作者已接受可观察结果，并且实现及对应迭代文档均已 commit 并同步到作者指定的共享 Git 历史。建议验证或版本级验证可以尚未完成，但每项已知缺口都必须准确记录，且不得视为通过。完成后不得改变迭代的历史范围、证据或结果；仅可修正已识别的事实或链接错误，并且不得改变其历史含义。
- `Cancelled` 表示作者在完成前停止迭代。必须记录取消日期、原因、已经交付或部分交付的工作、受影响的产品或技术契约、依赖和迁移后果、已有代码或数据的处置，以及后续迭代必须采取的措施。取消本身不授权回退或删除工作。
- 迭代完成不代表正式版本完成。适用版本契约独立管理版本级验证、签名、制品追踪、归档和发布结果。
- 必须准确记录已知缺口、失败、跳过场景、受影响行为和后续归属。未执行或无法执行的检查不等于通过。
- 准确标明来源的作者构建、安装或真机使用结果报告，可以作为其所含观察范围内的有效迭代证据；它不证明被省略的命令、环境身份、可复现性或更广泛验证结果。
- Agent 的日常实现不要求自动运行 Gradle。只有作者提出要求，或获授权的更高层验证任务需要时，才由 Agent 执行 Gradle 验证。
- 只有项目作者明确将某项检查提升为迭代门禁，或适用的更高层契约要求它作为正式版本、产物、签名、归档或发布结果的条件时，该检查才是强制项。
- 迭代推进不表示正式版本完成；适用版本契约继续保留独立的完成与发布门禁。
- 迭代完成表示记录中的所选范围和验收标准已经完成，不表示当前产品契约（包括该契约后续发生的变化）已经完整实现。

```markdown
# 迭代 <number>：<迭代标题>

> 适用版本契约与非授权边界

## 状态

- Value: `Planned`
- Updated: YYYY-MM-DD
- Basis: <当前状态值的依据；适用时包括作者决定或同步证据>

## 目标
## 产品和版本引用
## 可观察结果
## 纳入工作
## 排除工作
## 技术影响面
## 依赖和序列
## 迁移和兼容性影响
## 安全、隐私、权限和许可证影响
## 风险和未解决决定
## 验证计划
## 验收证据
## 相关决定、commit 和 tag
## 最终结果
## 剩余问题和交接
```

## 字段规则

- `状态` 为必填部分，`Value` 必须与枚举值之一完全一致。`Updated` 记录最近一次状态转换日期，而不是普通内容编辑日期。`Basis` 简要记录支持该状态的证据和作者决定；状态为 `Completed` 时，应标明已同步的实现和文档历史，或链接到相应记录。若同步目标不是常规共享 Git 分支，应标明作者指定的共享历史，但不得加入机器特定信息或秘密信息。
- 不引起状态转换的内容修改不得改变 `Updated` 日期。状态内的实质范围小调整应记录在正文相关章节和 Git 历史中。如果产品契约变化实质影响迭代目标、主要结果、验收标准或边界，应在完成前记录明确的范围修订；否则应取消并替换迭代，不得静默改变其含义。
- `Objective` 描述一个内聚交付结果，不是互不相关的任务清单。
- `Product and version references` 链接当前产品来源及同目录的 `delivery.md`。当契约变化的时间点会影响理解时，应记录适用的产品契约基线或来源修订，不得复制这些文档。
- `Observable outcome` 描述迭代成功后可演示或验证的结果。
- `Included work` 定义正向且可观察的交付边界。`Excluded work` 只记录否则可能被误认为已纳入的边界性非目标，不要求枚举迭代未包含的全部行为。只有确认后续归属或未来承诺时才使用“延期”。
- `Technical change areas` 在持久层级标识受影响行为、组件、接口、数据、构建与验证表面；逐行变更仍以 Git 为准。
- 只有实际考虑过某一影响领域后才能写 `None identified`，不得静默省略重大影响。
- `Validation plan` 列出建议场景，并标识任何被明确提升为强制项的检查；`Acceptance evidence` 记录实际观察的命令、环境、设备、结果和无法执行的检查，不得把缺失证据视为通过。
- `Final result` 记录可观察结果以及支持 `Completed` 或 `Cancelled` 的作者决定；处于 `Planned` 或 `In Progress` 时，应说明尚无最终结果。`Remaining issues and handoff` 记录全部已知证据缺口、后续责任人和下游影响。满足上述规则时，建议验证不阻塞 `Completed`，但文档不得宣称未执行检查已经通过。
- 迭代可以建议产品或技术决定，但不授权该决定。

版本完成时，迭代记录继续保留在稳定的 `docs/delivery/<version>/` 目录中，并适用上述历史保护规则。编号继续使用全项目序列；例如完成包含 `iteration-7-...` 至 `iteration-10-...` 的版本后，下一个可用编号为 `11`。
