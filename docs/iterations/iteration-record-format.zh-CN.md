# 迭代契约格式

> 英文语义源：[iteration-record-format.md](iteration-record-format.md)。

## 目的与命名

每个 `docs/delivery/<version>/` 目录为该版本纳入的每个迭代保存一份独立迭代契约。每个迭代是边界明确、可独立评审并服务于一个正式版本的交付单元。

迭代文档是稳定的产品交付契约，定义所选目标、范围、约束、验收条件和验证要求。它不负责项目执行状态、实际证据、commit 或最终结果。同目录的版本 `delivery.md` 是迭代状态和交付历史的唯一权威来源。

文件名使用 `iteration-<number>-<title>.md`，全项目采用从 `1` 开始、单调递增的正整数唯一序列，例如 `iteration-1-home-minimum-usable-surface.md`。不得重编号、复用或重启序列，也不添加前导零。`<title>` 使用简短的小写英文 slug。

维护中文对应文档时，在 `.md` 前追加 `.zh-CN`，例如 `iteration-1-home-minimum-usable-surface.zh-CN.md`。中文文档使用相同迭代编号和英文 slug。

## 必需格式

新迭代契约使用以下结构。获得授权后可通过修改本文调整格式；已有历史记录不因后来格式变化而重写。

中文对应文档可以翻译标题和章节标题，但必须与英文语义源保持相同的章节顺序、范围和规范含义。

## 契约与验证政策

Avenor Launcher 当前由项目作者作为个人项目维护。因此，迭代契约中的验证要求默认是降低风险、完善证据的建议；只有项目作者或适用的更高层契约明确将其设为强制项时，它才构成门禁。

- 每个迭代都必须有独立契约，不得用 `delivery.md` 中的章节替代。
- 每份新迭代契约必须使用完整的 40 位 Git commit ID 标明一项已接受的产品契约基线。该基线 commit 必须包含所选范围依赖的全部产品规则。生产实现继续前，实现任务线必须基于或以其他方式包含该基线。
- 契约不包含 `Planned`、`In Progress`、`Completed` 或 `Cancelled` 状态。同目录的版本 `delivery.md` 负责这些状态值、转换日期与依据、实际证据、最终结果和已知交付缺口。
- 迭代尚未完成时，允许按作者方向修改契约。如果修改会实质改变目标、主要结果、产品范围、架构方向、依赖顺序、验收条件或验证义务，必须在契约中明确记录修订。修订必须记录日期、作者决定、原因、原边界、新边界以及受影响的验收或验证义务。若修改会替换迭代身份，应通过版本交付记录取消并替换该迭代，不得静默重写契约；在已取消的交付行中链接替代契约，并在替代契约中链接已取消迭代。
- 版本交付记录将迭代标记为 `Completed` 或 `Cancelled` 后，不得改变契约的历史范围或验收含义；仅可修正已识别的事实、链接或翻译错误，并且不得改变其历史含义。
- 版本交付记录必须链接本契约，并记录实际命令、环境、设备、结果、跳过或无法执行的检查、失败、后续归属、相关 commit 或 tag，以及支持当前状态的作者决定。未执行或无法执行的检查不等于通过。
- 准确标明来源的作者构建、安装或真机使用结果报告，可以作为其所含观察范围内的有效交付证据；它不证明被省略的命令、环境身份、可复现性或更广泛验证结果。
- Agent 的日常实现不要求自动运行 Gradle。只有作者提出要求，或获授权的更高层验证任务需要时，才由 Agent 执行 Gradle 验证。
- 迭代完成不表示正式版本完成；适用版本契约继续保留独立的完成、验证、签名、制品追踪、归档与发布门禁。
- 该状态归属分离规则适用于新建及之后修订的记录。已有历史迭代文档可以作为 legacy 历史保留原有状态、证据和结果章节；不得仅为采用本规则而重写它们或回填版本交付记录。

```markdown
# 迭代 <number>：<迭代标题>

> 适用版本契约与非授权边界

## 目标
## 产品和版本引用

- 产品契约基线：`<完整 40 位 Git commit ID>`
- 适用产品文档：`<链接；有助于定位时包含章节锚点>`
- 适用版本契约：`delivery.md`

## 可观察结果
## 纳入工作
## 排除工作
## 技术影响面
## 依赖和序列
## 迁移和兼容性影响
## 安全、隐私、权限和许可证影响
## 风险和未解决决定
## 验收条件
## 验证要求
## 相关决定和技术评估
```

## 字段规则

- `Objective` 描述一个内聚交付结果，不是互不相关的任务清单。
- `Product and version references` 记录已接受产品契约基线的完整 40 位 Git commit ID，链接该修订下适用的产品来源，并链接同目录的 `delivery.md`。该基线是包含已接受产品定义的既有 commit，不是将要包含迭代文档自身的 commit、分支名、工作树描述或预计实现 commit。迭代从这些来源中选择交付子集，不复制其行为或表现规则。
- `Observable outcome` 描述迭代成功后可演示或验证的结果。
- `Included work` 定义正向且可观察的交付边界。`Excluded work` 只记录否则可能被误认为已纳入的边界性非目标，不要求枚举迭代未包含的全部行为。只有确认后续归属或未来承诺时才使用“延期”。
- `Technical change areas` 在持久层级标识受影响行为、组件、接口、数据、构建与验证表面；逐行变更仍以 Git 为准。
- 只有实际考虑过某一影响领域后才能写 `None identified`，不得静默省略重大影响。
- `Acceptance criteria` 说明可用于验收迭代的可观察条件。`Validation requirements` 定义建议场景并标明任何被明确设为强制项的检查，但不记录执行结果。
- `Related decisions and technical assessments` 只链接理解本契约所需的持久决定和评估。版本交付记录负责实现 commit、tag、实际证据、最终结果和剩余交付问题。
- 迭代可以建议产品或技术决定，但不授权该决定。

## 产品契约基线变更

迭代尚未完成时，如果已接受产品契约发生变化，应先判断迭代身份是否保留，再继续生产实现。

- 对于保留目标和主要验收结果的有界变化，增加一项已授权的实质修订。记录日期、作者决定、原因、原完整基线 commit、新完整基线 commit、变化的产品文档链接，以及受影响的范围、验收或验证义务。依赖实现继续前，实现任务线必须包含新基线。
- 如果变化替换了目标、主要结果或迭代身份，应依照现有替换规则，通过版本交付记录取消并替换该迭代。
- 不相关的产品契约 commit 不会仅因版本更新而改变迭代基线。只有所选范围依赖该项已接受变化时，才更新基线。
- 不得仅为采用本格式而向已完成或已取消的历史契约回填基线 commit。

版本完成时，迭代契约继续保留在稳定的 `docs/delivery/<version>/` 目录中，并适用上述历史保护规则。编号继续使用全项目序列；例如完成包含 `iteration-7-...` 至 `iteration-10-...` 的版本后，下一个可用编号为 `11`。
